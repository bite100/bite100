## 0. 地基：为什么可以拆节点

第 2 / 15 / 21 轮已经把**资金安全与结算正确性**从节点手里拿走了，这是整个
设计成立的前提，先钉死：

- **结算验签**：Settlement 对 maker/taker 双方订单做 EIP-712 验签
  （`docs/eip712-order-spec.md` 为唯一规范），中继者只是搬运工，断言不了
  任何金额；
- **防超额重放**：合约按订单 digest 累计记账 `orderFilledIn/orderFilledOut`
  + nonce 独占，同一订单不可能被结算超过其签名量；
- **无锁不结算**：Vault 落锁由合约从验签后的签名订单派生金额，结算时
  `consumeOrderLock` 无记录即 revert；用户资金始终在 Vault，不经过任何
  节点/中继保管；
- **费用与 gas 规则在合约内**：0.01% 交易费（FD 99% / 开发者 1%）与第 21 轮
  gas 对半回收 / 失败归责都在结算层执行，与谁提交无关。

因此节点今天真正独占的只有四件事：**传播、订单簿存储、撮合、中继提交 +
行情 API**。无节点化逐项替换这四件（§1），不动托管与结算。本轮不改合约、
不动金库轮（第 18 轮暂停状态不变，金库只在 §7 预留接口）。

订单消息格式不变：EIP-712 签名订单 + 未签名消息字段（`side`、`execType`、
交易对字符串，见 `node/internal/storage/orders.go` 的 `storage.Order`）。
公告栏里流转的就是今天 gossip 广播的同一份 JSON，任何渠道转发都不影响
真实性——验签在前端本地做一遍、结算合约再做一遍。

## 1. 四项职能逐项替代

### 1.1 传播

| | |
|---|---|
| 现状 | 节点间 libp2p GossipSub 广播订单/成交、Kademlia DHT 做对等发现；浏览器经节点 REST/WS 接入（前端 `nodeClient.ts`，多节点容灾列表） |
| 替代 | maker 前端把签名订单 POST 到轻中继（公告栏，§2 选型）；taker 前端按交易对拉取 / 订阅增量。订单自带签名与过期时间，公告栏只做存与转，不需要被信任 |
| 失去 | P2P 网络的传播冗余与「无固定入口」的理论抗审查性；节点间自动收敛出的近似全局视图 |
| 得到 | 无 libp2p 运维、无对等发现与 NAT 问题；前端直达数据源，少一跳；传播层可多源并行（见下） |
| 残余风险 | 单个中继可**藏单**（收了不展示）或延迟。中继藏单不伤资金，但伤该单的成交机会。缓解是结构性的：订单是可移植便签，maker 可同时发给多个中继、前端默认多源合并去重（按 digest）；某个中继藏单只会让它自己的用户看不到，不构成全局封锁。选型上 B（Nostr）把这点做到最强，A/C 靠多开镜像补 |

### 1.2 订单簿存储

| | |
|---|---|
| 现状 | 每节点 SQLite 落盘 + 内存订单簿，启动时恢复未过期 open/partial 订单（第二十二轮实证）；节点接单时先校验可用余额、驱动落锁成功后才入簿——簿上单必然链上有锁 |
| 替代 | 中继只做**哑存储**：按 (链, 交易对, 方向) 索引未过期签名订单，入库前验签 + 校验 expiresAt + 按 digest 去重；不撮合、不排序裁决、不记成交状态。每个前端拉回后本地验签重建订单簿，并用**链上状态二次过滤**：`Vault.orderLocks[digest]` 存在且 remaining > 0、`Settlement.orderFilledIn/Out` 未达签名量、未过期，三条全过才算「可吃单」 |
| 失去 | 「入簿即有锁」的串行保证：公告栏上的单可能处于「已发布未落锁」「锁已释放但中继未下架」的中间态，展示层必须靠链上过滤把幽灵单剔除或标灰（§4 给出落锁时序） |
| 得到 | 存储无状态、可替换、可多开；前端的簿是自己验签 + 读链重建的，不信任中继的任何断言 |
| 残余风险 | 幽灵单被 taker 选中 → 提交结算必 revert → taker 白付 gas（§3.3 的处理：提交前模拟拦截 + 归责口径）。中继存垃圾单的成本由入库验签与限流控制（§2） |

### 1.3 撮合

| | |
|---|---|
| 现状 | 各节点本地价格-时间撮合（`node/internal/match/engine.go`）；领导者把成交组装为提案（`consensus.go` 的 MatchProposal，含订单簿哈希），BFT 投票确认后才由中继提交 |
| 替代 | taker 前端本地撮合（§3）：在自己重建的簿上按价格-时间规则选 maker 单、按 maker 价组装 Fill、直接提交结算。仓库本就有一份浏览器内撮合实现（路线图 §2.8 记录的前后端双轨之一），本设计等于宣布**前端实现转正、Go 引擎退役为参照实现与测试向量来源** |
| 失去 | 全局一致的撮合序列：不再有「同一时刻全网一份簿、一份成交序」的近似，也不再有领导者排序的公平性背书；价格-时间优先退化为近似（§3.2 逐项明说） |
| 得到 | 零撮合基础设施；taker 完全自主（选哪张单、吃多少、何时提交都在自己浏览器里）；撮合逻辑一份实现，不再有 TS/Go 双轨漂移 |
| 残余风险 | 双 taker 竞态（§3.3）；跨前端簿视图秒级不一致导致的无效提交；市价单扫簿的原子性取舍（§3.2/拍板项 3） |

### 1.4 中继结算 + API

| | |
|---|---|
| 现状 | 节点以运营私钥单笔提交 `settleTrade`（`node/internal/settlement/submit.go`），撮合参数错误在节点预检层拦截、不到链上失败；失败扣费申报 `chargeFailedSettlement` 也由节点侧入口发起。API 为节点 REST（/api/trades、/api/orderbook、/api/orders、/api/health、/api/node）+ /ws 推送 |
| 替代 | 拆两半：①结算提交改为「谁撮合谁提交」——taker 自提 / 任意第三方代提 / 公告栏附带的提交机器人 / 将来金库签名者兼任，四种提交者角色在第 21 轮 gas 模型下逐一论证（§7）；②API 改为中继只读聚合 + 前端链上事件重建（§5） |
| 失去 | 运营方统一提交带来的预检拦截与批量均摊机会（批量入口仍在，需要时由提交者自己组批）；节点 WS 的即时撮合播报 |
| 得到 | 协议不再依赖单一运营私钥在线；提交者可替换、可竞争；成交以链上确认为准，数据口径反而更诚实（§5） |
| 残余风险 | 提交前预检责任转移到前端（模拟调用是必备件，不是可选项，§3.3）；公开 mempool 里 fill 可被第三方抢先提交——但 fill 内容被双方签名绑死，抢先者提交的结果与原提交者完全一致且 gas 回收归抢先者，对 maker/taker 无害（§3.4） |

## 2. 轻中继（订单公告栏）选型：3 个候选

共同前提（三者都必须满足，选型选的是实现载体，不是功能清单）：

- **入库验签**：中继收到订单先验 EIP-712 签名与 expiresAt、按 digest 去重，
  验不过不存——垃圾单的成本必须回到发送者一侧，中继不做免费垃圾场；
- **无钥无钱**：中继不持有任何用户私钥、不经手资金；它能做的最坏的事是
  藏单与延迟（§1.1），不能偷钱、不能伪造成交；
- **可移植**：订单格式与中继无关，迁移/多开时 maker 重发一遍即可，前端
  多源合并是默认形态。因此本节拍板的是**第一个上线的主中继**，不是终身
  绑定。

### 候选 A：Cloudflare Workers + D1（serverless 中继）

- 形态：Worker 提供 POST /orders（验签入库）、GET /orderbook、增量订阅
  （轮询/SSE）；订单存 D1（SQL，按链/交易对/地址建索引查询方便；KV 是
  最终一致且不擅长这类多维查询，只作缓存备选）。域名直接复用
  `node.aaxx123456.trade`（Ren 的域名与 CF 账户现成）。
- 理由：**运营成本最低**——无常驻进程、按请求计费，测试网与早期量级基本
  落在免费额度内；与现有域名/DNS/前端同域，CORS 与证书零摩擦；全球边缘
  延迟低；第 22 轮已证明这个域名体系可用（虽然当时连接器借道了电脑隧道，
  Worker 则原生跑在 CF 边缘，连隧道都不需要——顺带摘掉「Ren 电脑必须
  开机」这个现行依赖）。
- 代价：**供应商锁定 + 抗审查最弱**：CF 可以关停 Worker/账户，届时公告栏
  整体下线（订单可移植，需另有镜像兜底）；验签要在 Worker 内做
  （WebCrypto 不直接支持 secp256k1 ecrecover，需引入纯 JS/WASM 实现，
  是真实的接入工作量）；D1 有行数/查询限额与最终一致窗口（公告栏场景
  可接受）；免费层条款随平台政策变。

### 候选 B：Nostr 公共中继（订单即 Nostr 事件）

- 形态：订单 JSON 编码为 Nostr 事件（NIP-01，应用数据类 kind，如
  参数化可替换事件），带 `pair` / `digest` / `chain` 标签，发布到多个
  公共 relay；前端按标签过滤订阅多 relay 并合并。订单真实性仍由其内嵌的
  EIP-712 签名保证；Nostr 的 Schnorr 密钥只是传输层邮差身份（前端可用
  派生/临时密钥，因为邮差不需要被信任）。
- 理由：**抗审查与去单点最强**——现成无许可网络、无需任何人运营、无需
  Ren 的任何账户与域名；一个 relay 藏单/删单，换一个或多发几个即可；
  运营成本为零。
- 代价：**数据层最不可控**：公共 relay 对自定义 kind 与垃圾的保留策略
  各异（可能不长期保存、可能限流、可能拒绝非主流 kind），查询能力参差
  （按标签过滤的支持度不一），漏单与延迟不可测；订单的「下架/撤单」
  只能靠事件提示 + 读端链上过滤兜底（与 §1.2 的设计兼容，但幽灵单
  比例会最高）；生态工具以社交场景为主，订单簿这种结构化查询要自己
  在前端拼。适合当**并行镜像**，不适合当唯一事实源。

### 候选 C：极简自托管哑中继（现节点瘦身版）

- 形态：从现有 Go 节点剥掉撮合、BFT、gossip、结算提交，只留与现
  `/api/orders` 形状对齐的哑 REST：POST 存单（验签后）、GET 拉簿、
  WS 推送；单文件 SQLite 或纯内存 + 周期快照。仍跑在 Muse VM（直接
  复用第 22 轮的 systemd、ensure.sh、看门狗与隧道入口），代码与运维
  与现行同构；任何人都可以照同一镜像再开一个，前端多源合并。
- 理由：**迁移成本最低、行为最可控**：入库验签、限流、过期下架、按地址
  查询全在自己手里；API 形状与现节点对齐，前端从双读到切换的改动
  最小；不引入任何新平台与新依赖（集成优先在本候选体现为「复用
  既有工件」）。
- 代价：**仍有一台要养的进程**——只是比全节点瘦得多（无共识无撮合后
  故障面小一个量级）；单点运营者仍是 Ren 自己，「抗审查」靠的是
  「镜像可复制」而非现成网络；现行入口借道 Ren 电脑隧道的毛病
  （电脑离线则公网入口断）原样保留，除非另配云主机（第 22 轮
  runbook 的云迁移路径同样适用于它）。

### 对比与推荐

| 维度 | A：CF Workers + D1 | B：Nostr 公共中继 | C：自托管哑中继 |
|---|---|---|---|
| 运营成本 | 最低（无服务器，近免费额度） | 零 | 一台小进程 + 现有运维 |
| 抗审查 / 藏单 | 弱（平台可关停） | **最强**（多 relay 冗余） | 中（靠镜像可复制） |
| 垃圾单防护 | 自行实现（验签需补 secp256k1） | 最弱（依赖各 relay 策略） | **最强**（全自控） |
| 上手与维护 | 中（新平台、新代码） | 中（协议适配 + 不可控性调教） | **最低**（现有代码瘦身） |
| 与现有域名契合 | **最好**（同域直用） | 无关（不需域名） | 好（沿用第 22 轮入口） |
| 数据可控性 | 中 | 最弱 | **最强** |

**推荐排序（最终由 Ren 定）**：**C 先行**（最快把无节点链路跑通、前端
改动最小、失败可退回现节点）→ **A 继之**（链路验证后把公共入口迁到
serverless，摘掉电脑开机依赖，成为长期主中继）→ **B 作并行镜像**
（抗审查冗余，不作唯一源）。三步是演进关系而非三选一互斥，但首发选
哪个决定先写哪套代码，故列为拍板项 1。

## 3. 前端撮合

### 3.1 taker 本地组装结算

1. 前端从公告栏（多源合并）拉对手簿，本地验签、按 §1.2 链上状态过滤，
   得到可吃单集合；
2. 用户选单/输量后，前端在本地按价格-时间规则（§3.2）确定 maker 单与
   成交量，成交价一律取 **maker 价**（与现行撮合的价格改善口径一致）；
3. 前端组装 `Fill`（maker/taker 双方 `SignedOrder` 全文 + 成交量），
   经 §7 的提交通道上链；Settlement 验签与累计记账是最后防线；
4. 限价 taker 单未成交的余量 → taker 自己的订单转为 maker 单发布到
   公告栏（挂单动作 = 发布 + 落锁，时序见 §4）；市价单余量不入簿
   （IOC 语义不变）。

实现纪律（后续实现轮的硬要求，先写进设计）：撮合计算必须用**定点整数**
（BigInt），不得沿用 Go 引擎的 float64 价格（路线图 §2.1 已记的确定性
差距）；TS 实现以「已上链的历史 Fill」作回归向量逐笔对账，Go 引擎在
退役后保留为参照实现。

### 3.2 价格-时间优先：能近似到哪一步、做不到哪一步

- **能近似**：价格优先无争议（签名价可比）；同价按订单签名内的
  `timestamp` 先后排序——timestamp 在签名覆盖内、可信；并列时以
  digest 字典序作确定性 tiebreak（可复现、无经济含义，仅为各前端
  结果一致）。
- **做不到，明说**：
  1. 「时间」从共识事实退化为**提交上链的先后**——没有全局排序者能
     证明某 taker 先看到某单；两个 taker 同时吃同一单时，谁的成交
     有效由区块顺序决定，不由订单簿时间决定；
  2. 各前端经不同中继看到的簿有秒级时差，可能选中**已被吃掉/已撤**
     的单，表现为结算 revert（处理见 §3.3）；
  3. 市价单扫簿无法像中心化撮合那样在单次撮合内锁定全簿深度：逐档
     组装期间簿会变。取舍二选一（拍板项 3）：**整批原子**——用
     `settleTradesBatch` 一笔提交全部档位，任一档失效整批回滚
     （语义干净、gas 按第 21 轮批量均摊，但一颗老鼠屎坏一锅）；或
     **逐档提交**——每档独立结算，已成交的落定、失效档跳过续扫
     （更贴近 IOC 直觉，gas 总额更高、部分成交状态更碎）。

### 3.3 双 taker 竞态如何收场（与第 21 轮失败归责的衔接）

场景：两个 taker 针对同一 maker 单组装了 fill，先上链者成交；后者的
交易被合约拒绝——触发点必居其一：累计成交超签名量（规范 §4-4）、
锁已耗尽或不存在（`consumeOrderLock` revert）、nonce 已被同签名者的
另一订单占用。**资金安全不受影响**（整事务回滚由合约保证），唯一
损失是后者白付的 gas。按第 21 轮规则逐项对照（这是关键衔接，写透）：

- 第 21 轮的失败扣费只认两类**链上可验事实**：`FAIL_ORDER_EXPIRED`
  （订单已过期）、`FAIL_LOCK_RELEASED`（锁被释放/撤单且未成交完），
  靠 Vault 落锁墓碑定被扣方。**「被别人抢先吃掉」不在两类之内**：
  锁不是被释放的，是被正常结算消费掉的，墓碑无法也不应把它归责
  于 maker；
- 因此竞态失败属于第 21 轮归责表里的**不可归责失败 → 提交者自担**。
  无节点后提交者就是 taker 本人（或其代提交者）——「失败算发起者」
  在无节点形态下字面回归：发起提交的人先垫、且在不可归责时终担。
  成功时不受影响：`GasCostShared` 照常从双方收到额对半扣给
  msg.sender，与谁先谁后无关；
- 例外通道保持不变：若 maker 在 taker 在途期间**撤单释放了锁**，
  taker 的结算失败正是 `FAIL_LOCK_RELEASED`，可由白名单申报方走
  `chargeFailedSettlement` 向 maker 收费（测试网已开启、上限
  5 quote；申报纪律见 §7）——撤单竞态与吃单竞态在归责上是两回事，
  合约分得清，前端文案也要分清；
- 前端必须把竞态损失压在事前：**提交前预检是必备件**——即时重读
  该 maker 单的链上 `orderFilled` 与 `orderLocks.remaining`，并对
  组装好的 fill 做 `eth_call` 模拟，模拟不过就不提交、不花钱。
  预检挡得住绝大多数（簿时差造成的）无效提交；挡不住的只剩
  「模拟通过后、交易上链前被抢先」的真实竞态窗口，其成本量级 =
  一笔结算 gas、且只在同单被抢时发生——这是无全局排序的固有
  成本，本设计如实记账，不假装能消除。

### 3.4 抢跑与公开 mempool

fill 的内容被双方签名绑死（订单、数量、价格改善都在合约校验内），
第三方在 mempool 看到后抢先提交，产出的链上结果与原提交**完全
相同**，且第 21 轮的 gas 回收会记在抢先者（msg.sender）名下——
抢跑者等于替原提交者垫了 gas 还拿回同一份回收，对 maker/taker
无害、对原 taker 仅有「自己的提交随后因已成交而 revert」的风险
（仍走 §3.3 预检 + 自担口径）。不存在改价、改量、截胡资金的
抢跑面；这是确定性 fill 与 AMM swap 的本质区别。

## 4. 订单生命周期：过期、撤销与落锁释放

### 4.1 现状接口盘点（读 Vault 代码实证，`contracts/src/Vault.sol`）

| 接口 | 权限 | 无节点后够不够 |
|---|---|---|
| `lockForOrder(order, sig, payWithTokenIn)` | **仅 locker 角色**（`onlyLocker`，:135） | ❌ **唯一缺口**：maker 本人调不了 |
| `consumeOrderLock` | 仅 Settlement，结算内自动调用 | ✅ 不变，无需任何人操作 |
| `releaseOrderLock(digest)` | locker **或锁属用户本人**（:184） | ✅ maker 自助撤单解锁，现成 |
| `releaseExpiredOrderLock(digest)` | **无权限**，过期即可调（:192） | ✅ 任何人可代释放，现成 |
| `orderLocks` / `lockTombstones` | 公开读 | ✅ 前端过滤与失败归责的凭据，现成 |

结论先行：**撤销与过期释放的自助路径今天就存在**，无节点化不需要
为它们动合约；全生命周期只缺第一步——**没有节点时谁来落锁**。

### 4.2 落锁缺口的三个方案（拍板项 2）

`lockForOrder` 的安全性来自「Vault 向 Settlement 验签 + 金额从订单
本身派生」，locker 只是付 gas 按按钮的人。放开它的方案三选一：

- **L1 自锁**：合约小改——允许 `msg.sender == order.userAddress` 的
  订单本人自锁（验签逻辑不动）。maker 挂单 = 签名 + 一笔自锁交易，
  gas 自付。与「存入/提取 Vault 的 gas 由用户自付」的既有口径一致，
  但偏离现行体验：今天落锁 gas 由运营节点代付，挂单对用户是零 gas
  的纯签名动作，L1 后挂单要备原生币（与北极星「用户不备 gas」在
  挂单环节有张力，虽然量小）。
- **L2 无权限落锁（推荐）**：合约小改——任何人可为任何**验签有效**
  的签名订单落锁。安全面逐项核过：金额由签名订单派生、锁的是签名者
  自己的钱、按其自签条款执行，伪造不可能；过期单被 `expiresAt`
  校验挡下；重复锁被 `orderLocks[digest].user == 0` 检查挡下。
  骚扰面只剩「替别人把已公开订单上锁」——而上锁正是公开订单的
  意图本身；若 maker 已改主意，其自助 `releaseOrderLock` 一笔即可
  解锁（成本一笔 release 的 gas）。运营上把「谁付落锁 gas」留给
  生态：公告栏运营方、提交机器人、taker 在吃单前顺手、maker 自付，
  都可；挂单零 gas 的现行体验得以保留。方向标志 `payWithTokenIn`
  仍由提交者给出（它只在订单自带的两个签名义务间二选一）：写错
  方向的锁会在结算消费时因口径不符 revert（资金安全兜底），前端
  在单上簿后应读 `orderLocks` 校验 (token, remaining) 与本意一致，
  不一致立即自助释放并告警——该校验列入实现轮清单。
- **L3 维持白名单**：不动合约，把 locker 授予公告栏运营方（或一个
  专用落锁机器人钥）。改动最小、今天就能跑；但 locker 又成为必须
  常驻在线的持钥角色，与去节点化目标部分相悖；且第十五轮已记的
  门禁「主网 locker 要换 leader/BFT 中继集合」在无节点后失去
  对应物，需另行定义。只建议作迁移过渡（§8 阶段 1–2），不作终局。

三者都只需改 Vault 一个函数的权限修饰 + 补 forge 测试；但注意
**换 Vault = 用户余额迁移问题**（第 21 轮已知限制 6）：测试网无
真实用户、可接受，主网若已上线则必须先有迁移方案——此点随
拍板项 2 一并记入主网门禁复核。

时序（L2/L3 下的挂单全流程）：maker 签名 → 发公告栏（状态：
已发布未落锁，前端展示层标「待确认」或不上正式簿）→ 落锁交易
上链（`OrderLocked` 事件）→ 前端读链过滤通过 → 进正式簿可吃。
这条「先发布后落锁」的时序比今天节点「先落锁才广播」多一个
中间态，是 §1.2 链上过滤存在的理由。

### 4.3 撤销与过期的无节点流程（接口全现成）

- **软撤单（零 gas）**：maker 把 `CancelOrder` 签名消息（规范 §5，
  三方已对齐）POST 给公告栏作下架凭据；中继下架，其他前端增量
  同步后不再展示。但软撤单不改变链上状态：锁仍在、单仍可被
  已持有该单的 taker 提交结算——与今天「节点监听事件下架」的
  竞态性质相同（撤单意图与在途成交赛跑）。
- **硬撤单（一笔 gas）**：maker 本人调 `releaseOrderLock(digest)`
  ——锁释放后该单再被提交必因无锁 revert，且在途成交的提交者可
  按 `FAIL_LOCK_RELEASED` 被归责（§3.3）。前端撤单按钮默认走
  硬撤单（确定性最强），软撤单作即时下架的先行动作，两轨并行。
- **过期**：公告栏按 `expiresAt` 自动下架；锁由任何人调
  `releaseExpiredOrderLock` 释放（前端在用户打开资产页时顺手
  代发即可），资金不会被永久锁死——该兜底今天已存在。
- **部分成交后撤单**：`releaseOrderLock` 释放全部 `remaining`
  （只剩未成交部分），既有语义不变。
- **市价单余量释放**（第十七轮 §2.5 的时序约束）：今天由节点
  轮询 `orderLocks.remaining`、待结算消费落链后精确释放余量；
  无节点后由 **taker 前端自己**做同一件事——taker 是该锁的属主，
  `releaseOrderLock` 本人可调；等待逻辑（轮询 remaining 降至
  应剩量）从 Go 代码改为前端代码即可，零成交时立即全额释放的
  分支同理。硬兜底仍是过期释放。

## 7. 中继者与 gas：第 21 轮模型下谁来提交结算

第 21 轮模型回顾（本节的约束条件，不重复设计）：成功结算的 gas
由合约链上计量、从 maker/taker 双方**收到额中各扣一半**转给
`msg.sender`（提交者），单方扣除有 10% 封顶、差额协议吸收；
失败只认 `FAIL_ORDER_EXPIRED` / `FAIL_LOCK_RELEASED` 两类
可归责事实，由 owner/治理/白名单 relayer 经
`chargeFailedSettlement` 事后申报、向被归责方收费（默认关闭，
测试网已开 5 quote 上限）；不可归责失败提交者自担；
`gasUsedClaimed` 不可链上验是已知限制。三种提交者逐一论证：

### 7.1 taker 自提

- 成立方式：taker 用自己钱包直接调 `settleTrade` /
  `settleTradesBatch`。提交前预检（§3.3）在本地完成。
- gas 账：taker 先垫 gas，结算成功后合约把**全额**回收
  （双方各半合成）以双方收到的资产形式转给 msg.sender =
  taker——taker 净承担的是自己那一半（以资产扣除，本来就该
  他付），垫付只是流动性占用，不是额外成本。
- 真实门槛，明说：钱包里**一分原生币都没有**的用户提不了
  ——这与北极星「用户不备 gas」在自提模式下有张力（现行模式
  是运营节点代垫、用户永不见 gas）。因此自提只能是**通道
  之一**，不能是唯一通道（见 7.2/7.3 兜底）。
- 优点：零信任、零依赖、随时可用；市价多档可一笔批量提交
  享受均摊。

### 7.2 任意第三方代提（无许可提交机器人）

- 成立方式：fill 是确定性内容，任何账户都可以拿去调
  `settleTrade`；公告栏运营方顺手挂一个提交机器人是最自然的
  实例（用户在前端点「成交」，机器人代提交），独立第三方
  亦可。
- gas 账：回收额被第 21 轮校准为**约等于、且宁可略低于实付**
  （`meterKeepBps` 的少收纪律），所以代提在纯 gas 账上至多
  打平、结构性略亏——**没有利润空间，也就没有「中继市场」**，
  代提只能是服务/补贴行为：其对价在链下（运营方的产品服务）
  或在贡献奖励的中继权重（§6 方向①正好衔接：按链上提交量
  记账补贴提交者）。这一点不粉饰：指望无许可中继自发竞争
  在现行回收口径下不成立。
- 失败风险：代提者提交失败且属不可归责类 → 自担 gas；
  属可归责类（过期/锁释放）→ 申报权在白名单内，默认代提者
  不在白名单内，垫付收不回。理性代提者的风控就是**提交前
  模拟**（与 §3.3 同一预检），把失败率压到近零后，剩余风险
  可忽略。
- 优点：用户零 gas 体验得以保留；机器人可替换（换运营方、
  或多个并行），协议层不依赖其中任何一个在线。

### 7.3 金库常驻签名者兼任（只预留接口，本轮不唤醒金库轮）

- 背景：做市金库第 2 档设计（`docs/market-maker-vault-design.md`，
  第 18 轮暂停中）本就规划了「链上登记的授权签名者、可交易
  不可提款」的常驻角色。它在线做市时，天然是最合适的提交者：
  自己的成交自己提交、顺手提交别人的 fill，回收 gas + 记
  中继贡献。
- 本设计只预留三点，不依赖金库时间表：① 提交接口不假设
  身份——合约现状即如此（任何 msg.sender 可提交），无需
  为金库改合约；② 失败申报白名单（`chargeFailedSettlement`
  的调用方集合）由治理管理，金库签名者上线时可经治理授予；
  ③ 前端提交通道做成可配置列表（自提 / 公告栏机器人 /
  未来金库端点），与 §2 的多源合并同构。金库上线前，提交
  通道由 7.1 + 7.2 覆盖，不留空窗。

### 7.4 失败申报者的归属

节点退役后，`chargeFailedSettlement` 的现实申报方 = 公告栏
运营方（提交机器人即它时，申报自己提交且 revert 的交易，
回执 gasUsed 在它手里，与第 21 轮的申报纪律完全一致）或
经治理授予白名单的金库签名者。申报纪律与不可验声明不变：

taker 自提被可归责失败坑掉时，可向运营方提供回执求申报
