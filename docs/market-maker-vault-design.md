# 做市金库设计（第十七轮 Part C · 只设计，不实现）

> **⚠️ 定位变更（2026-11-08，负责人拍板）：本篇的「做市金库」定位已被取代。** 金库不再做市，改为 **gas 库**——吸引存款人的资金作 gas 垫付周转金并吸收计量 shortfall，平台只做中介、不自营当交易对手。原 MakerVault 合约（ERC-4626 + 签名报价）的去向（改造/停用）待 gas 库机制定版后另轮处理；分成权重因本次改定**重算中、尚未拍板**，以最新决定为准。本篇正文保留为历史设计记录，不再作现行口径引用。

> 背景：第十七轮砍掉 AMM 后，盘口的「即时流动性」改走 Hyperliquid 路线——
> 由一个做市金库（Market Maker Vault）长期在订单簿双边挂单。本文给出
> 完整设计与三档托管模型供拍板；**本文不含任何实现**，落地等 Ren 选定
> 档位后另开轮次。
> 对标：Hyperliquid 的 HLP、dYdX 的 MegaVault。

---

## 1. 对标速览（两家的共同形状）

| | HLP（Hyperliquid） | MegaVault（dYdX） |
|---|---|---|
| 本质 | 协议金库：任何人可存入，份额按比例分享做市与清算收益 | 协议金库：用户存入 USDC，分享做市收益 |
| 做市执行 | 协议原生做市策略（平台自己运营） | 由指定运营方（做市商）操作金库资金做市 |
| 收益来源 | 做市价差、清算罚金分成、资金费等 | 做市价差与返佣 |
| 份额与退出 | 按份额占比赎回，有锁定期（存入后约 4 天才能提） | 按份额赎回，收益以年化形式呈现（可变、非承诺） |
| 风险承担 | 存款人按份额承担策略亏损（极端行情下金库存量会亏） | 同左 |

**共同点，也是本设计的基本盘**：金库不是理财产品，是一台「众筹的做市商」——
存款人出钱、按份额分盈亏；做市本身照常走订单簿、照常付费/结算。区别只在
谁拿着钥匙做市（托管模型，见 §3）。

## 2. 与本项目架构的衔接（为什么金库在本项目里天然成立）

本项目的交易链路是「EIP-712 签名订单 → 节点撮合 → Vault 余额结算」。
金库在这条链路里**不需要任何特殊通道**，它就是一个体量很大的普通交易者：

1. 金库的资金以普通用户身份存入 **Vault**（第十五轮的余额/锁定模型现成）；
2. 做市程序以金库身份**签限价单**挂进订单簿（双边报价，见 §5）；
3. 成交后由 Settlement 按既有路径结算、扣 0.01% 手续费（与所有人同价）；
4. 存款人份额、金库净值（NAV）记在**链下账本或金库合约**里（按档位不同，
   见 §3/§4）——交易与结算层零改动。

衔接点小结：签名订单格式、撮合、锁定、结算、手续费**全部复用**；新增的
只有「金库自己的账本 + 做市程序 + 资金进出通道」。

## 3. 三档托管模型（核心决策）

### 档位 1：运营方托管 EOA（最简单）

- 形状：存款人把钱打给运营方的一个普通钱包（EOA）；运营方用这个钱包
  在 Vault 存款、签单做市；份额与盈亏记在链下账本（网页后台 + 定期公示）。
- 代价：工程量最小——做市程序 + 一页份额账本即可，无合约、无再部署，
  可最快上线验证「金库做市在本盘口是否赚得到价差」。
- 风险：**全托管**——运营方（或其密钥）可以把钱转走，存款人只能靠信任
  与事后对账；运营方跑路/密钥被盗 = 存款全损。适合小额、熟人圈、试点期；
  不适合公开募集。

### 档位 2：合约金库 + 链上登记授权签名者

- 形状：写一个 Vault 托管合约持有全部资金；合约在链上登记 1..N 个
  **授权签名者**地址——签名者只能以金库身份签单、把金库在 Vault 里的
  余额用于交易（经一个「做市代理」合约把金库资金存入交易 Vault 并以
  登记签名者的签名下单），**不能提款**；提款只有存款人按份额发起、
  且只能打回存款人本人地址。份额记账在合约内（§4）。
- 代价：需要新合约 + 审计 + 一次再部署与接线（交易 Vault 本体可不动，
  新增的是金库合约与代理）；签名者密钥轮换、暂停都走合约治理。
- 风险：运营方作恶面被合约关死到「只能乱交易、不能搬钱」——乱交易仍能
  把金库亏光（故意以坏价格与关联账户对敲），需再配合 §6 的链上可验
  风控（报价偏离中间价上限、单笔/单日量上限写进代理合约校验）；
  合约自身 bug 是新增风险面，审计必备。本档是**信任与工程量的平衡点**。

### 档位 3：协议金库（节点网络原生做市，最接近 HLP）

- 形状：做市成为节点网络的原生职能——金库资金由协议合约持有，做市
  策略由节点网络按与撮合相同的共识路径执行/复核（报价即网络行为），
  收益与份额完全链上化；运营方退化为参数治理者（价差、库存上限经
  Governance 投票设定）。
- 代价：工程量最大——做市策略要进节点代码并处理多节点一致性（谁报价、
  如何防重复/冲突、策略参数的共识），加上协议金库合约与治理接线；
  且策略 bug 的影响面是全网性的。
- 风险：无单点托管风险，但**策略即协议**——极端行情下全网金库同向亏损
  无人能临时干预（熔断逻辑必须事先写进协议）；开发与审计成本最高、
  周期最长。适合交易量与用户规模真正起来之后。

### 三档对照

| | 档位 1 EOA 托管 | 档位 2 合约金库 | 档位 3 协议金库 |
|---|---|---|---|
| 存款人信任对象 | 运营方本人 | 合约代码 + 审计 | 协议 + 治理 |
| 运营方能提款 | **能**（全托管） | 不能（只能交易） | 不能（无此角色） |
| 运营方能亏光金库 | 能 | 能（乱交易，需链上风控收口） | 策略性亏损，无单方作恶 |
| 合约改造/再部署 | 无 | 有（金库+代理合约） | 有（协议级） |
| 份额记账 | 链下账本 | 合约内 | 合约内 |
| 工程量粗估 | ~1–2 周 | ~4–6 周（含审计等待） | ~2–3 个月起 |
| 适合阶段 | 试点验证 | **正式开放存款** | 规模化后 |

## 4. 份额记账（存入 → 份额 → 盈亏累积 → 按份额退出）

- **计价资产**：本项目交易对为 TKA/TKB 双资产盘口，金库须同时持有两种
  资产库存。份额统一以 **quote 资产（TKB）计价 NAV**：每个记账 epoch
  （建议每日）快照金库在 Vault 中的两种余额，base（TKA）按当期盘口
  中间价折 quote，`NAV = TKB 余额 + TKA 余额 × 中间价`。
- **存入**：存款人存入 quote（或 base，按中间价折 quote 入账）→
  `获得份额 = 存入折算额 × 总份额 / 存入前 NAV`（首存 1:1）。存入的钱由
  金库按目标库存比（§5）换成双边库存——注意：这一步换仓本身要走盘口
  交易（小额盘口会有滑点，试点期可由运营方在外部补齐，设计上记为已知
  约束，不假装不存在）。
- **盈亏累积**：不单独分红——做市盈亏直接体现在 NAV 上（份额单价涨跌），
  与 HLP 同构；手续费按普通交易者照付（§7）。
- **退出**：按份额占比赎回 `NAV × 我的份额 / 总份额`，以 quote 支付为主、
  base 部分按中间价折 quote（金库库存不足 quote 时触发一轮再平衡卖出，
  因此赎回设 **T+1 结算 + 提款冷静期（如 24–72 小时，档位 2/3 由合约
  强制）**，与 HLP 的锁定期同一目的：防挤兑把库存砸穿盘口。
- **记账可验性**：档位 1 靠公示对账（地址公开，任何人可核 Vault 余额与
  成交记录）；档位 2/3 份额与 NAV 输入（Vault 余额）全部链上可读，
  NAV 计算规则写进文档/合约，任何人可复算。

## 5. 做市策略草案（试点参数，全部可调）

- **报价**：围绕盘口中间价双边挂限价单（中间价取金库外订单簿 best
  bid/ask 中点；盘口为空时退化为最近成交价，再无则暂停报价）。
- **价差**：基础半价差 0.15%（买 = mid × (1 − 0.15% − 库存偏斜)，卖对称）；
  波动放大时自动加宽（如以近 1 小时波动率分档 0.15% / 0.3% / 0.6%）。
- **库存偏斜（skew）**：base 库存高于目标时，买价额外下压、卖价同步
  下压促卖出（线性偏斜，上限 ±0.3%）；目标库存比默认 50/50（按 quote
  折算）。
- **单档量**：每边同时挂 3 档（近/中/远价差），单档量 = 金库 NAV 的
  1–2%，总在簿量 ≤ NAV 的 30%。
- **刷新**：中间价变动 ≥ 0.05% 或每 30 秒（取先到）全量撤旧挂新；
  撤/挂都是普通签名操作（第十五轮锁定随挂单自动落锁/释放，天然兼容）。
- **再平衡**：库存偏离目标 > 20 个百分点时，用市价单（第十七轮 Part B）
  在自家盘口外……盘口只有自家时再平衡无对手——试点期再平衡走「调报价
  等自然成交」为主、市价单只在有外部挂单时用；跨链库存调拨可用既有
  LayerZero 桥（测试网 DVN 状态与主网门禁不变，见第十六轮记录）。

## 6. 风控

| 风控项 | 草案 |
|---|---|
| 最大库存 | 单资产库存（折 quote）≤ NAV 的 70%；base 净敞口另设硬顶 |
| 单边暂停 | 库存触顶 → 停挂该方向买单（防越买越多）；NAV 单日回撤 > 5% → 双边停挂待人工/治理确认 |
| 坏行情熔断 | 5 分钟内中间价变动 > 3%，或盘口/节点数据异常（无成交价参考）→ 立即全撤并暂停，恢复需手动或超时自动（参数可选） |
| 报价偏离护栏 | 任何报价偏离中间价不得超过 ±2%（档位 2 由代理合约链上校验，档位 1 由程序自检+公示） |
| 签名者密钥 | 做市签名密钥与运营方主钱包分离、单独保管；档位 2 支持链上轮换/吊销；泄露时先吊销签名者再处置资金 |
| 提款挤兑 | 冷静期 + T+1（§4）；金库在 Vault 的余额被挂单锁定的部分本就不可提（第十五轮模型天然防超提） |
| 对敲/自成交 | 金库订单与普通订单同路撮合，不给金库任何优先级；档位 2+ 公示金库地址，任何人可审计其成交 |

## 7. 与手续费、贡献奖励的关系

- **手续费**：金库照付 0.01% 交易费（与所有交易者同价）——不给自家金库
  开费率后门，保持盘口规则可信；金库付出的手续费按既有 FeeDistributor
  路径分配（开发者 1% 等现状不变）。
- **贡献奖励「流动性 20%」权重再分配**（第十七轮 Part A 遗留：AMM 下线
  后该权重失去原对象，现挂账待拍板）。候选方案：
  - **A. 改为「金库存入」权重**：按存款份额 × 存入时长加权计分——把原
    「提供流动性」的激励平移到新流动性来源，与金库冷启动互相成就；
  - **B. 拆分**：10% 给「金库存入」、10% 并入「撮合」——兼顾存款人与
    撮合节点，金库激励减半、冷启动力度弱一些；
  - **C. 改为「盘口挂单」口径**：不再绑 AMM，按任意用户在订单簿的在簿
    深度 × 时长计分（订单簿版流动性）——激励分散到所有挂单者，但计分
    实现要进节点统计，工程量最大；
  - **D. 并入撮合（40% → 60%）**：最简单，但流动性一侧再无任何激励，
    金库冷启动全靠价差收益自证。
  建议 A 或 B（与金库冷启动同向）；最终由 Ren 拍板后与金库档位一并落地。
  在此之前权重保持 20% 不动。一个必须在金库落地前处理的检查项：现行
  `ContributorReward.submitLiquidityProof` 是签名证明计分通道（与 AMMPool
  无运行时耦合，未随 Part A 下线）——新口径拍板前，治理应明确该通道按
  什么计分，避免旧口径在无对象状态下被继续使用。

## 8. 分阶段落地建议

| 阶段 | 内容 | 前置 | 工程量粗估 |
|---|---|---|---|
| P1 试点 | 档位 1：运营方 EOA + 做市程序（§5 参数）+ 链下份额账本页 + 地址/账本公示 | 无（现架构直接可做） | 1–2 周 |
| P2 正式 | 档位 2：合约金库 + 授权签名者 + 链上风控护栏 + 审计 + 再部署；P1 账本迁移 | P1 跑出真实价差收益数据、Ren 拍板档位 2 | 4–6 周（含审计） |
| P3 协议化 | 档位 3：节点原生做市 + 治理定参 | 交易量/用户规模达到需要去运营方的程度 | 2–3 个月起 |

推荐路径：**先 P1 小额试点验证收益模型，再决定是否投 P2**——HLP 式金库
的生死不在托管档位，而在盘口价差收益能否覆盖库存亏损，先用最便宜的
档位把这件事测出来。

## 9. 需要 Ren 决定的一件事

**做市金库先落哪一档托管模型？**

- **选 1（运营方托管 EOA）**：最快上线试点、零合约风险；代价是存款人
  全信任运营方，只适合小额试点与熟人范围。
- **选 2（合约金库 + 授权签名者）**：正式开放存款的信任底线（能交易、
  不能提款）；代价是合约开发 + 审计 + 一次再部署，周期 4–6 周。
- **选 3（协议金库）**：一步到位最接近 HLP、无单点信任；代价是工程量
  与周期最大（2–3 个月起），且策略 bug 即协议 bug。
