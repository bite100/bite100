## 0. 命题与范围

今天的跨链成交是两段手动动作：用户先在桥页选通道、把币搬到成交链，
再回来下单（或成交后自己再搬回去）。本设计消掉这段手动搬运：

- 用户**预先**在设置里选定一条默认桥（四通道四选一：LayerZero /
  Chainlink CCIP / Wormhole / 做市商极速到账），选的那一刻完成与桥页
  同等强度的完整披露（§2.3）；
- 之后跨链成交**自动**按收款方各自的默认桥发起交付（§1），逐笔只
  显示一行非阻断预计（§4.1），不弹窗、不重选；
- 等待时间等于所选桥的真实时效（§3）——LZ 档与极速档是「几分钟」，
  CCIP / Wormhole 档是「十几分钟」，文案逐通道如实写，不许混写。

**不在本设计范围内**：改结算为跨链原子（不可能也不需要，§1.1）、
自建 filler/solver 网络（极速档集成现成聚合器，§2.4）、链抽象/聚合
余额（OneBalance 的 Toolkit API 已于 2026-05-18 弃用，见调研 §6）、
净额轧差清算（Everclear 已于 2026-05-21 停运，不作依赖，见 §9）。

## 1. 总时序：结算单链原子，跨链只发生在交付腿

### 1.1 为什么结算是单链原子的（既有地基，不动）

Bit100 的结算从来不是跨链的：第 2/15/21 轮已把成交做成**成交链上一
笔交易内的 Vault 余额互换**——Settlement 验双方 EIP-712 签名、Vault
按订单 digest 记账与落锁、交易费与 gas 对半回收都在同一笔交易内执
行。两条链之间不存在这种原子性（没有任何机制能让 Sepolia 的合约与
Base Sepolia 的合约同时成功或同时回滚），因此**任何设计都不该把结
算拆到两条链上**。跨链问题在 Bit100 里只剩一个位置可解：结算**之
后**，收款方把成交款从成交链送回自己主场链的**交付腿**。本设计自
动化的只有这一条腿。

推论（第一期边界，先钉死）：结算的前置条件不变——成交双方在成交
链的 Vault 里都须有可用余额，订单才能被结算。交付自动化解决的是
「成交款怎么回家」，不解决「付款款从哪来」；付款腿的自动补款
（成交前经默认桥自动注资成交链 Vault）**不在第一期**（见 §10），
前端在余额不足时仍按现行口径提示，另给一键「经默认桥补款」的普通
桥页入口（那是逐笔手动桥接，不是本设计的自动交付）。

### 1.2 跨链成交时序

同链成交（成交链 = 收款方主场链）**完全不变**，无交付腿。跨链成
交按以下时序（对 maker / taker 两个收款方向各独立走一遍）：

```
撮合（订单所在链的订单簿，现行机制不变）
  → 结算：成交链上单链原子结算（现行机制不变，双方 Vault 余额互换）
  → 交付判定：收款方主场链 ≠ 成交链 且 其默认桥设置有效
      → 否：成交款留成交链 Vault，流程结束（状态「无需交付」）
      → 是：查支持矩阵（§6）定通道：
          默认桥支持 → 默认桥；否则按三级回退（§6）定通道或挂起询问
  → 交付发起：与结算同一编排流程内，从收款方成交链 Vault 余额中
    提出成交款、存入所定桥的通道合约（幂等绑定，§7.1）
  → 交付在途：状态机推进，带通道名、预计时间、桥追踪链接（§4.2）
  → 终态：已到账（款落收款方目标链地址）/ 交付异常（落点见 §7.3）
```

状态机（每笔成交 × 每个收款方一条交付记录）：

```
已成交 → 待交付判定 → 无需交付（终态）
                    → 交付发起 → 交付中 → 已到账（终态）
                                   ↘ 交付异常（终态，带落点与可执行操作）
```

### 1.3 先例同构：CoW Swap 的 swap-and-bridge（调研 §2.4）

「先成交、后过桥」不是自创形态：CoW Swap 已出货的 swap-and-bridge
正是 swap 先在源链结算、成交款在**与结算同一笔交易内**由预签名
post-hook 自动存入桥服务商合约，用户零额外操作，UI 只呈现
「Bridging in progress → Bridging completed」；订单过期/取消/失败
则桥接永不启动、资金留钱包；桥存入一旦提交不可取消。与本设计的
唯一差别：CoW 的桥是逐笔在订单里选的，Bit100 换成**用户预设的默
认桥**——预设这一层由 LI.FI 的 `allow / prefer` 桥偏好语义提供工
业先例（调研 §1.1：`allow` = 硬白名单、`prefer` = 软偏好，两档语
义均为其 API 原生参数）。付款腿先行（先跨钱再交易）的时序等于把
今天的手动流程提前，不解决命题；双腿原子并行只有 hashlock / 垫付
模式能做，那是极速档的定价方式（§2.4），不是默认通道的形态。

## 2. 默认桥设置规格

### 2.1 设置数据模型（每用户一份）

| 字段 | 内容 |
|---|---|
| `defaultChannel` | 四选一：`layerzero` / `ccip` / `wormhole` / `fastlane`（极速到账），可为未设置 |
| `homeChain` | 交付目标链（用户的主场链）；成交链与之相同则无交付腿 |
| `fallbackOrder` | 可选的备选通道顺序（第二期，§6 二级回退；每个备选须各自完成披露确认） |
| `confirmations[]` | 逐通道确认记录：`{channel, disclosureVersion, confirmedAt}`（§2.3） |
| `standingAuth` | 常设交付授权：用户签署的常设指令，授权编排器在结算后从其成交链 Vault 余额发起桥存入；授权范围 = 已确认披露的通道集合 |

存储位置随基础设施阶段走（现阶段节点/前端侧记录，无节点阶段迁
D1），**数据模型本身在本设计定死**、不随存储位置变。实施轮须定的
接口点（本设计只定语义）：常设授权的载体——Vault 侧 opt-in 标记
（用户一笔链上交易置位）或用户签名的常设指令 + 编排器代行，二选
一由实施轮按合约改动量评估后在轮次文档中定版；无论哪种，授权必
须**可撤销**（用户在设置页关闭即失效，关闭后新成交不再自动发起
交付，在途交付不受影响、必然走完）。

### 2.2 设置入口与流程

- **入口**：桥页（在四通道列表上方加「我的默认通道」设置区）为主
  入口；资产页与「其他」页各放一行入口（「跨链交付设置：默认通道
  X / 未设置 ›」），与第 31 轮骨架设计的页面分工一致。
- **流程**：进入设置 → 四通道并列（每条给费率结构、时效区间、安
  全模型一句话）→ 点选一条 → 进入该通道的**完整披露屏**（§2.3）
  → 用户勾选确认并保存 → 生效。此后跨链成交自动执行，不再逐笔
  询问。
- **改选**：改选默认桥 = 对新通道重走完整披露屏；**已成交待交付
  的订单不受影响**，按成交时生效的默认设置执行（此口径须写进设
  置页文案，调研 §1.5）。

### 2.3 披露规格（承诺点全披露——知情选择的前移形态）

点选某通道为默认的那一屏，披露强度**与桥页确认前披露同等**，必
含以下要素（缺一不可上线）：

1. **费率结构**：该通道的费用构成（桥协议费 / 目标链 gas 的承担
   方式 / 极速档的价差口径），以**动态读取的当前值或近期区间**呈
   现——**禁止把费率写死进文案**（调研 §8：各桥主网费率的实时数
   字须实施轮按路线实测，设置页接实时/近期费率）。
2. **时效区间**：按 §3 的逐通道真实区间（含「等待主要由成交链的
   确认/终局规则决定」一句白话解释）。
3. **安全模型**：谁在验证这条消息——LZ 的 DVN 组合、CCIP 的 DON +
   Risk Management Network、Wormhole 的 19 个 Guardian、极速档的
   solver 垫付与回款机制，各用白话一段。
4. **具体风险点**：含 **LayerZero 当前 1-of-1 DVN 现状的白话说明**
   （选 LZ 时必显：「目前只有 LayerZero 官方一家在验证，等于信任
   这一家」——与桥页现行口径一致）；LZ 用区块确认数而非全终局的
   概率性确认说明（§3）；极速档的 solver 对手方风险。
5. **不可撤销**：交付一旦发起不可取消、必然走完（消息桥无取消
   概念，§7.2）。
6. **失败时资金去向**：该通道的三段式失败口径摘要（§7.4），含异
   常落点 = 退回成交链 Vault 余额（§7.3）。

**版本与确认记录（硬性要求）**：每条通道的披露文案有独立版本号
`disclosureVersion`；用户每次确认都落一条记录（通道、版本、时间，
§2.1 的 `confirmations[]`）。**文案改版后旧确认失效**：下一次该
通道被用作默认交付前，用户须在设置页重新确认新版披露；在重新确
认前，跨链成交照常结算、但该通道的自动交付**挂起**（成交款留成
交链 Vault，订单历史中标注「交付待确认：披露已更新，请到设置页
重新确认后补发」），不弹窗阻断交易本身。

### 2.4 极速档：第二十轮 LI.FI 通道升格为默认选项

四通道中的「做市商极速到账」即第 20 轮已集成的 LI.FI solver 快
线（`frontend/src/services/fastLane.ts`，零合约改动）——本设计只
是把它从桥页的一个选项**升格为可被选为默认的一档**，其既有约束
照旧、且必须写进它的披露屏：

- **主网限定**：测试网在服务商层被硬拦，标注「主网功能 · 测试网
  不可用」，不得伪造报价（第 20 轮口径）；
- **前置动作在 Ren**：生产可用以 Ren 在 LI.FI Partner Portal 自助
  注册并取得免费 API key（填 `VITE_LIFI_API_KEY`）为前提，未取得
  前极速档在主网同样不可选为默认；
- **资产覆盖**：只覆盖 solver 有库存的主流资产，长尾资产走 §6 回
  退；费用为价差 + 协议费（调研口径 4–8 bps 量级，结构性数字，
  具体报价逐笔实时读取）。

### 2.5 使用说明（随功能同轮上线，功能变更带说明规则）

设置页本身即说明书，须让新用户只看页面就能操作，至少讲清四件
事：**干什么**（选一次默认通道，之后跨链成交的钱自动送回你的主
场链，不用再去桥页搬）；**使用前提**（已连接钱包、成交链 Vault
有余额、在途交付不可撤销）；**操作步骤**（选通道 → 读披露 → 确
认 → 生效；改选与关闭自动交付的位置）；**注意事项**（时效逐通道
不同、桥费由收款方承担的口径在 §5 拍板后写定、披露更新后需重
新确认、失败时钱退回成交链 Vault 不会丢）。每笔成交的预计行
（§4.1）与交付状态（§4.2）文案同属本节的说明面。

## 3. 时效口径表（主网与测试网分开，禁止混写）

等待几乎全部由**源链（= 成交链）的终局/确认规则**决定，与目标链
无关。主网口径（调研 §3 核查结论）：

| 默认通道 | 主网端到端（常见 EVM 路线） | 用户文案口径 | 依据与折让说明 |
|---|---|---|---|
| LayerZero | 通常 **2–6 分钟**（以太坊源 15 区块确认 ≈ 3 分钟 + DVN 验证 + Executor 投递；L2 源确认数更少、本身秒级出块） | 「几分钟」 | 速度来源是**用区块确认数代替全终局**——这是风险折让（概率性确认，理论短重组风险），必须随文案披露，不能只报快 |
| 极速到账（LI.FI） | **秒级–5 分钟** | 「几分钟内，通常更快」 | solver 垫付、与源链终局解耦；「Across ~2 秒」为厂商口径，**不写进文案** |
| Chainlink CCIP | 默认 **15–20 分钟级**（等源链全终局；连 Base/Arbitrum 源也 ~17–18 分钟，因其等 L1 终局标记） | 「十几分钟」 | CCIP 2.0 FTF 的「12–24 秒」只是确认信号口径、逐路线启用未核实（调研 §8），**禁止引用进文案** |
| Wormhole | **约 15 分钟级**（以太坊锚定路线含 L1 终局；L2 源约 5 分钟） | 「十几分钟」 | 二手证据等级（调研 §8 未取得官方逐字口径），实施轮须按具体路线复核后再定版文案 |

测试网口径（项目内实测，第 16/19 轮，**单列、不得与主网混写**）：
LZ ≈ 458 秒、CCIP ≈ 20 分钟、Wormhole ≈ 59 分钟（测试网无自动
relayer、人工中继补投递）。测试网数字只用于测试网环境的页面标注
与验收对照，不代表主网。

补充一条全局口径：未来若成交发生在以太坊主网，全部消息桥通道
都会被以太坊终局拖到 15 分钟量级（solver 垫付的极速档除外）——
设置页时效文案须按**当前成交链集合**动态生成区间，不写脱离链的
绝对数字。

## 4. 每笔成交的呈现

### 4.1 成交前：一行非阻断预计

凡本次成交将产生跨链交付腿的，在下单/成交确认区固定呈现一行
（非弹窗、不要求点按、不阻断）：

> 交付：成交款将经你的默认通道 LayerZero 送回 Base，预计费用
> ≈（实时读取），预计 3–6 分钟到账。

字段口径：通道名 = 实际将用的通道（若已触发 §6 二级回退，写实
际通道名并标注「默认通道不支持本笔，已按你的备选顺序改用 X」；
三级回退的成交前询问是唯一允许打断的形态，见 §6）。费用与时间
均为实时/近期口径的**预计**，与最终值不一致时以交付记录为准、
不构成报价承诺——此句须在设置页说明中讲明（先例：CoW 把桥成
本折进「最低到账」单行披露；THORChain 系前端在确认前展示三段
费用与预计确认时间，调研 §1.5）。

### 4.2 成交后：交付状态的展示位与字段

展示位：**订单列表 / 历史订单**内，每笔成交下挂其交付记录（不新
建页面孤岛；资产页对应链的余额行在「交付中」期间给在途金额标
注）。交付记录字段：

| 字段 | 说明 |
|---|---|
| 状态 | 无需交付 / 交付发起 / 交付中 / 已到账 / 交付异常（§1.2 状态机） |
| 通道 | 实际执行的通道（回退时为实际通道，§6） |
| 金额与费用 | 交付金额、实际桥费（与结算 gas 分开记账，§5） |
| 预计/实际时间 | 发起时预计区间；到账后实际耗时 |
| 追踪链接 | 通道对应的浏览器/追踪页（LayerZero Scan、CCIP Explorer、WormholeScan、极速档的聚合器状态页） |
| 异常信息 | 异常时的落点说明与用户可执行操作（重试交付 / 提取到钱包，§7.3） |

## 5. 费用口径（2026-11-08 已拍板：收款方承担）

两笔账分开（调研 §7 清单第 6 条）：**结算 gas** 维持第 21 轮规则
（结算时双方对半分摊、以成交资产抵扣），与本节无关；本节只定
**交付桥费**（把成交款从成交链送回收款方主场链的桥协议费 + 目标
链投递 gas）。

- **推荐：收款方从自己的成交款中承担。** 理由：交付是收款方单边
  的事——把钱送到哪里只服务于收款方一人，另一方不受益；且双向
  成交时 maker/taker 各是自己那笔的收款方，各付各的、账目天然对
  齐（CoW 的 swap-and-bridge 亦是桥成本从成交款侧扣除、折进最低
  到账）。文案上与结算 gas 分开两行呈现，不许合并成一个「费用」
  数字。
- 备选 A：买卖对半分摊交付费。利：与 gas 对半收的直觉一致、口
  径统一好讲。弊：未受益方为对方的回家路买单；当只有一方跨链、
  另一方同链时仍要分摊，账目与公平感都别扭。
- 备选 B：付款方承担（计入其付款额）。利：收款方到账金额干净。
  弊：交付费随通道与行情浮动，计入付款额会污染订单的签名价格语
  义（成交价不再等于签名价），与现行结算记账冲突最大。

本节为**拍板项**（见 §11 第 1 条）；未拍板前，设置页文案中该处
留占位口径，不得先行上线含糊表述。

## 6. 支持矩阵与三级回退（默认优先，永不静默回退）

「不支持」是三维的：**桥 × 链对 × 资产**——极速档只覆盖主流资
产、某些资产只走特定桥（OFT 类之于 LZ、NTT 类之于 Wormhole、
CCIP 的代币池目录）、某些链对在某桥根本没上线。Bit100 的交易对
是配置化上架（第 25 轮），因此**支持矩阵在上架时静态算出**：每
个交易对落一张「四通道 × 该对资产」的支持表（数据形态参照 LI.FI
`GET /v1/tools` 的 `supportedChains` 与各桥官方目录，实施轮按通
道逐项核对），驱动下列三级回退：

1. **一级（默认路径）**：默认桥支持本笔 → 自动执行，只显示 §4.1
   的非阻断预计行。绝大多数成交走这一级。
2. **二级（预授权备选）**：默认桥不支持、但用户在设置时预授权了
   备选顺序（每个备选在其被加入备选时同样完成 §2.3 全披露并落确
   认记录）→ 按序自动改用第一个支持的备选通道执行；交付记录与
   预计行**明示实际通道**（事后可知、不静默）。先例边界：LI.FI 的
   `prefer` 语义可借鉴其数据形态，但其回退是静默的——**静默部分
   不借鉴**（调研 §5）。本级为第二期上线（§10），第一期只有一级
   与三级。
3. **三级（无预授权可用）**：该笔在**成交前一次性询问**（唯一允
   许打断的情形——它落在用户从未承诺过的通道上），选项为：临时
   选一条支持的通道（选前给该通道完整披露）/ **只在成交链交付**
   （成交款留成交链 Vault，不跨链，用户日后自行处理）。用户也可
   在设置里预先把「无备选时」定为「一律只在成交链交付」，从而永
   不被询问。

目录层红线：**四通道全不支持跨链交付的交易对，上架即标注「仅
同链交易」**，不让用户形成可自动交付的预期（先例：THORChain /
Chainflip 在目录层拦截不支持的资产对，CoW 以能力声明明示不支
持的形态，调研 §5）。

## 7. 失败与异常

### 7.1 发起绑定与幂等（不许出现「成交了但交付没发起」）

交付发起必须与结算**绑定为同一编排流程**（先例：CoW 的 post-hook
与结算同交易模式）：结算提交器在确认结算成功后，于同一流程内为
每条待交付记录发起桥存入；每条交付记录以（成交 ID × 收款方）为
幂等键，编排器重启/重扫后凭幂等键去重，**同一笔成交款永不重复发
起两次桥存入**。结算失败/订单未成交 → 交付永不启动（状态机无此
路径），成交款的归属只由结算结果决定。

### 7.2 消息桥的失败语义：失败 ≈ 延迟，没有「取消」

LZ / CCIP / Wormhole 三条消息桥**没有取消概念**：消息一旦发出即
不可撤销、必然走完；实际失败多表现为**延迟而非丢失**（投递重试、
Executor/relayer 迟到）。产品上需要的因此不是退款按钮，而是三
件套：**状态追踪**（§4.2 的追踪链接与状态机）、**超时告警**
（超过该通道时效区间上限仍未到账 → 交付记录转「交付异常：超
时」并通知用户与运营侧）、**人工中继兜底**（Wormhole 的 VAA 人工
补投递路径已在第 19 轮测试网实测跑通；LZ 的无许可 `lzReceive`
补投递为第 9/16 轮既有经验；CCIP 以其官方人工执行口径为准，实
施轮核对）。极速档的失败语义不同（未填充可在源侧取消/退款，聚
合器状态含 `DONE + REFUNDED` 终态，调研 §4），按其披露屏口径
单独处理，不与消息桥混写。

### 7.3 异常落点预登记：退回成交链 Vault 余额

每笔交付在发起前预登记异常落点，统一定为**退回收款方在成交链
的 Vault 余额**——资金回到用户在 Bit100 内的账本，是最自然的落
点（调研 §4 设计红线）。两类异常区别处理：

- **发起失败**（桥存入未成功，如通道合约异常/费用不足）：款从未
  离开 Vault，交付记录标注失败原因，用户可在订单历史里点「重
  试交付」（重走 §6 通道判定）或「提取到钱包」自行处理；
- **在途异常**（已发出但超时/投递失败）：按 §7.2 先走追踪与人工
  中继兜底；只有在通道侧确认该消息终局失败（如可证的投递放弃）
  时，才按预登记落点把等额款项记回成交链 Vault 并通知用户——在
  通道侧未确认失败前，**不许双记账**（同一笔钱不能既在途又回
  账）。

资产页须能看到异常落点里的余额与上述两个操作入口（与第 31 轮资
产页「可用/锁定中/钱包」三数口径衔接，异常回账计入成交链可用
余额并给来源标注）。

### 7.4 失败文案：三段式（借鉴 PancakeSwap 跨链 FAQ 结构）

每条通道的披露屏与帮助文案按三段式写定（先例见调研 §4）：

1. **交付发起失败** → 钱在哪（成交链 Vault，一分未动）、你能做
   什么（重试交付 / 提取到钱包）；
2. **在途超时** → 怎么查（追踪链接）、预计上限多久、超限后谁介
   入（人工中继兜底）；
3. **目标侧入账异常** → 钱的最终落点（§7.3）与到账后的操作。

文案随通道逐条落字，不许四条通道共用一段模糊表述。

## 8. 选项 C 预留：小额垫付即时到账（不进第一期）

调研给出的增强项，本设计只留**接口与触发条件**，不展开实现：

- **形态**：用户默认桥照常预设；另设金额阈值，成交款 ≤ 阈值时
  由平台垫付池在收款方主场链即时交付（体感秒级），垫付池随后经
  用户的默认桥回补库存；> 阈值走选项 A 的异步交付。先例：
  THORChain 按金额缩放确认数与出金延迟、Chainflip 的 Boost 垫付
  层（LP 垫付、收费 0.05%–0.3%）——「金额决定速度档位」是已验
  证的出货范式（调研 §2.1、§2.5 选项 C）。
- **资金结构预留**：垫付金库复用第 27 轮 MakerVault 的 ERC-4626
  范式另设合约，**与做市金库分账、分风险**；垫付池的库存错配与
  桥在途风险由平台承担（与选项 A 的「用户自担所选桥风险」不
  同），须有池子上限、单笔上限与异常熔断——这些参数不在本设计
  定数。
- **触发条件（满足才立项）**：选项 A 上线后，按真实跨链成交的
  **金额分布与笔数分布**再定阈值与池子规模（调研 §7 清单第 8
  条）；在此之前任何「先把池子建起来」的动作都不做。
- **接口预留点**：交付编排在 §1.2 的「交付发起」一步预留执行方
  选择（桥通道 / 垫付池），交付记录加 `executor` 字段；第一期该
  字段恒为桥通道，状态机与 UI 不因 C 的预留而改变。

## 9. 硬门与边界

1. **LZ 多 DVN 硬门不变**：默认桥选 LayerZero 时，主网开放仍以
   多 DVN 配置执行并回读验证为前提（现行 1-of-1 是上线门，不是
   文案能绕过的；本设计不改变该门的任何结论）。其余通道的主网
   门槛按各自既有轮次结论（CCIP/Wormhole 的主网执行器/自动中继
   决策、极速档的 LI.FI API key 前置，§2.4）。
2. **桥页手动通道保留不变**：桥页四通道逐笔手动桥接照旧；默认
   桥设置只是新增的自动化层，不删手动路径。
3. **知情选择规则不取消、只前移**：披露发生在承诺点（设置/改选/
   加入备选时）+ 每笔非阻断预计行 + 回退永不静默——三条缺一，本
   设计即退回「静默预选」的违规形态（调研 §1.5 判定）。
4. **不新增外部依赖**：第一期只复用第 19 轮三桥与第 20 轮 LI.FI
   的既有集成；Everclear（已停运）与 OneBalance（已弃用）不作
   依赖（§0、调研 §6）。
5. **测试网先行**：全部功能先在 Sepolia + Base Sepolia 双测试网
   验收（§10），主网开放逐通道过各自硬门后另行拍板。

## 10. 实施拆分与验收标准

### 第一期：选项 A 骨架（默认设置 + 交付编排 + 状态机 + 回退一/三级）

范围：§2 设置（入口、数据模型、披露屏与版本确认记录、常设授权
与撤销）、§1.2 交付编排与结算绑定（§7.1 幂等）、§4 状态机与订
单历史呈现、§6 支持矩阵 + 一级/三级回退 + 「仅同链交易」标注、
§7.4 三段式文案、§2.5 使用说明随功能同轮上线。

验收标准（全过才算完成）：

1. **双测试网跨链成交 E2E**：Sepolia ↔ Base Sepolia 两个方向各
   至少一笔真实跨链成交走完「结算 → 默认桥（LZ）自动交付 →
   已到账」，交付记录字段完整、追踪链接可达；CCIP 与 Wormhole
   各至少一笔（Wormhole 测试网以人工中继兜底走完为验收口径，
   与第 19 轮实测一致）。
2. **同链回归**：同链成交无交付腿、行为与现行完全一致；未设置
   默认桥的用户跨链成交后款留成交链 Vault、无任何自动动作。
3. **失败注入**：模拟桥存入失败 → 款留 Vault、状态与文案正确、
   「重试交付」可成功；模拟在途超时 → 告警触发且**不双记账**；
   编排器在结算后、交付发起前重启 → 凭幂等键补发且不重复发起。
4. **回退路径用例**：默认桥不支持某对 + 无预授权 → 成交前询问
   出现且「只在成交链交付」可走通；四通道全不支持的交易对带
   「仅同链交易」标注且无交付入口。
5. **披露版本用例**：文案版本号 bump 后，旧确认失效、自动交付
   挂起、补确认后可补发；改选默认桥不影响在途交付。

### 第二期（视第一期数据决定，不预先承诺）

范围：§6 二级回退（预授权备选顺序的设置 UI 与自动执行）；选项
C 的立项评估（触发条件见 §8）；付款腿自动补款的再评估（§1.1
边界项，若真实用户卡点在此则提出新设计）。

验收标准：二级回退全路径用例（默认不支持 → 按预授权序改用备
选、实际通道在预计行与交付记录双处明示）；C 若立项，另行出设
计补充稿定阈值与风控参数后再动工。

## 11. 拍板清单（2026-11-08 Ren 已全部按推荐定版）

> **2026-11-08 定版**：Ren 确认四项全部按推荐——① 交付桥费由收款方从成交款承担（与结算 gas 分账）；② 第一期只上三条消息桥（LZ/CCIP/Wormhole）默认设置，极速档待主网与 LI.FI API key 就绪后补入；③ 常设授权第一期只做全量开关 + 可撤销，额度上限随第二期设计；④ 无备选时出厂默认「成交前询问一次」。

1. **交付桥费由谁承担**（§5）：推荐**收款方从成交款承担**（与结
   算 gas 对半收分开记账、分开文案）；备选 A 买卖对半 / 备选 B
   付款方承担（与签名价格语义冲突最大）。
2. **第一期通道范围**：四通道中极速档受 LI.FI API key 前置与主
   网限定约束，测试网不可用——第一期是否只上三条消息桥（LZ /
   CCIP / Wormhole）的默认设置，极速档待主网与 key 就绪后补入
   （推荐如此），还是第一期就把极速档设置位与披露一并做齐、仅
   执行层后置。
3. **常设授权的撤销与额度**：是否给常设交付授权加单笔/单日金
   额上限（超限的交付改为成交前逐笔确认），还是第一期只做全量
   开关（设置开 = 全部自动、关 = 全部不自动）。推荐第一期先做
   全量开关 + 撤销，上限随第二期与选项 C 的风控一并设计。
4. **「无备选时」的默认处置**（§6 三级）：出厂默认是「成交前询
   问一次」还是「只在成交链交付」——前者多一次打断但不让钱默
   默留在外链，后者零打断但用户可能事后才发现钱没回家。推荐
   「成交前询问一次」（与不静默原则一致）。
