## 2. B 批：现行代码修复（第 6–10 项）

### 6. 节点签名缓存键未绑定订单内容（engine.go）

- **根因**：`signatureCache` 只以 orderID 为键——同一 orderID 换内容/换签名会命中旧验证结果，订单簿可被污染（链上结算仍会复验，不构成资金盗取，但簿内状态不可信）。
- **改法**：缓存键改走代码库既有的统一口径——`OrderDigest(BuildSignedOrder(order, pairTokens))`（即 Vault 按摘要落锁、Settlement 验签的同一 EIP-712 摘要）与签名字节拼接后取 keccak256。摘要计算失败时不缓存、直验（fail-closed）。
- **测试**：`TestIsSignatureValid_CacheKeyBindsContentAndSignature`——同 ID 篡改金额 → 不命中且验签失败；同摘要换签名者 → 失败；原单仍命中缓存为真。

### 7. 订单簿满员静默截断（engine.go AddOrder）

- **根因**：单交易对上限 10000 时，追加路径会静默丢弃尾单且不清理 `orderIDToPair` 索引，簿与索引不一致。
- **改法**：满员改为**拒绝新单**（沿用 AddOrder 现有 bool 返回约定）；索引只在订单真正入簿后写入；拒绝时顺带清理同对的陈旧同 ID 索引项；同 ID 替换先移除旧单（释放名额）再入簿。
- **测试**：`TestAddOrder_CapacityRejectsNewKeepsIndexConsistent`——恰 10000 时新单被拒、簿量与索引一致、同 ID 替换不被误拒。

### 8. GossipSub 未接 DHT 发现（host.go / main.go）

- **根因（比审查发现更深一层）**：不只是「未接发现」——`StartDHT` 从未在 main.go 被调用，DHT 根本没有启动过。
- **改法（只骑库、自研为零）**：main.go 新增启动步调用既有 `p2p.StartDHT(ctx, h, cfg.Network.Bootstrap)`（失败不致命，降级 kad=nil 继续）；`NewGossipSub` 在 kad 非空时追加 go-libp2p-pubsub 官方的 `pubsub.WithDiscovery(routing.NewRoutingDiscovery(kad))`（kad-dht 自带的 routing discovery 实现）。host.go 过时注释与 config.example.yaml 的 bootstrap 说明同步改正（空 bootstrap 合法，但孤节点需至少一个入口才能开始发现）。
- **测试**：`TestGossipSub_DHTDiscoveryDelivers`——两个本地 host，B 的唯一入口是 A 的 DHT bootstrap，消息经发现通道送达（约 3 秒）。
- **上线实证**：新二进制启动日志出现 DHT 启动行（双节点均已确认，见 §4）。

### 9. 前端治理 ABI 漂移（config.ts / GovernanceSection.tsx）

- **根因**：合约 `getProposal` 返回 9 字段，前端 ABI 只声明 8 个（缺 `executableAt`）；组件按位置解构时把 executed/executableAt 错位，治理页状态文案（投票中/可执行/时间锁等待中/已执行）与真实状态不符。另发现组件实际调用的 `getMultiStepProposal` 在 ABI 中根本不存在（其回退调用必然抛错）。
- **改法**：`GOVERNANCE_ABI` 补 `getProposal` 的 `uint256 executableAt`、补齐 `getMultiStepProposal`（按合约 10 字段精确签名）、ProposalCreated 的 target 改 indexed、Voted 补 weight；组件单步/多步两处位置解构同步修正，页面说明文字与修正后的状态口径核对一致。
- **ABI 自动生成评估**：仓库现无从 forge 产物生成 ABI 的既有模式（config.ts 全部手写）。本轮**不新建生成管线**，仅在此备案方案：后续可由 `contracts/out` 的 artifact JSON 经脚本抽取 ABI 写入 config.ts 并在 CI 加漂移校验——待治理真正接线时与门禁（§6）一并落地。

### 10. Vault.deposit 名义金额记账（Vault.sol）

- **根因**：`deposit` 按调用方声明的 `amount` 记账，未核实实际到账；若上架转账扣费/重基准代币，账面余额将大于实际持仓（现行交易对均为标准代币，无现实暴露，属条件性风险）。
- **改法（只动 deposit 一处）**：transferFrom 前后各读一次 `balanceOf`，以差额 `received` 为实收记账并发事件；`received == 0` 时回滚。不改接口、不牵动 Settlement/MakerVault。
- **测试**：新增 `contracts/test/VaultDeposit.t.sol`——带转账扣费的 mock 代币存 1000 实记 900、提取与账面一致无幻影资金；标准代币行为不变。

## 6. C 批：启用前门禁（只写文档，不动代码）

以下两项为 ChatGPT 审查发现中「代码事实成立、但功能未启用、无现实暴露面」的条目。本轮不修代码，改为落字门禁：**启用条件未全部满足前，不得接线/启用**。contracts/README 的 Governance 与 NodeRewards 条目各有一行指向本节。

### ① Governance 接线前必修

- **现状**：`_createProposal` 允许提案人自填选民集 Merkle 根与 activeCount，通过线为 yesCount > activeCount>>1——提案人可自造选民集自投通过。现行技术栈中 Governance **未接线**：双链 Settlement/Vault 的 owner 均为部署者 EOA，治理合约地址仅存在于前端旧配置，无任何核心合约受其控制，**无现实暴露面**。
- **启用条件（全部满足才可把任何核心合约 owner 交给 Governance）**：
  1. 活跃选民集改为由链上 NodeRegistry 登记快照产生，提案人不得自填；
  2. 选民集提交权与提案权分离（提交快照与发起提案为不同角色/流程）；
  3. 补单地址自选民攻击测试（自造根 + 自投 + 时间锁后执行 全链路用例）并通过；
  4. 前端治理 ABI 改由 forge 产物自动生成（见 §2 第 9 项备案方案），消除手写漂移。

### ② NodeRewards 启用前必修

- **现状**：`bindAndRegister` 对 nodeId 无全局唯一性校验、亦无在线/贡献真实性验证——任意地址可抢注/冒领。现行双链 `Settlement.nodeRewards()` 均为零地址、**未启用**，第 29 轮的配对脚本与证据测试处于待命状态，无现实暴露面。
- **启用条件（全部满足才可把 nodeRewards 指针写入 Settlement 并接入奖励发放）**：
  1. nodeId 全局唯一登记（先占先得、不可覆盖，登记表上链可查）；
  2. 可验证的在线/贡献证明机制落地（仅自称在线不计奖励）；
  3. 抢注/冒领/女巫三类攻击用例补测并通过。
