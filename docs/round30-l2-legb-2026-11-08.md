## 2. L2 滥用面评估（逐项对照）

形式：先例风险 → 对照结论 → 依据（Vault 语义/代码位置）。

| # | 先例 / 风险 | 结论 | 依据 |
|---|---|---|---|
| 1 | **Arcdesk dust-lock DoS**：无 bond 的无权限落锁曾被用来造大量碎片化小额锁占位/骚扰，其修复是按 (orderId, payer) 分键 | **不成立** | 本 Vault 的锁**没有金额参数**：`lockForOrder(order, sig, payWithTokenIn)` 的锁定量恒为签名订单的全额义务（amountIn 或 amountOut），不存在「小额锁/dust 锁」的构造方式；锁以**订单 digest 为唯一键**（`orderLocks` 以 bytes32 digest 为键），且 `require(orderLocks[digest].user == address(0))` 使同一订单无论由谁调用都只能落锁一次——没有按 payer 分裂的键空间可占。Arcdesk 的病根（按锁分片 + 可任意定额）在本语义下不存在 |
| 2 | 攻击者凭空锁定他人资金 / 锁别人没签过的量 | **不成立** | 落锁前 Vault 强制经 Settlement 验签（`verifyOrderSignature`，含 ERC-1271 合约路径）并由 Settlement 计算 digest；锁定代币、金额、归属（`orderLocks.user`、`lockTombstones`）全部由验签后的订单派生，调用者无法传入金额、无法指定归属、无法伪造锁定键；且只能动签名者本人在 Vault 的预存余额（`availableBalance >= amount` 校验） |
| 3 | 攻击者抢锁 maker 已签但改主意的订单，冻结其余额（骚扰） | **残余存在，低危** | 成本近似对称：攻击者付一笔 lock gas，maker 付一笔 `releaseOrderLock` 即可自助解锁（锁属用户本人有权，语义未动），攻击者无任何资金收益；占用时间有硬上限——订单 `expiresAt` 一到，任何人可 `releaseExpiredOrderLock`；maker 也可弃用该 orderId/nonce 重签新单。锁定的始终是 maker 自己签过的条款，不存在被迫履行未同意交易的情形 |
| 4 | 方向标志 `payWithTokenIn` 被第三方写反 | **有界残余（fail-closed + 读回校验）** | 订单为交易对朝向、方向不在签名覆盖内，标志只能由落锁者给出（第 15 轮以来的既有设计，L2 只是把「谁能给」从白名单扩到任何人）。写反的后果：maker 在另一侧代币无余额时落锁直接 revert（forge 用例 `test_L2_WrongDirectionFlagFailsClosed` 覆盖）；maker 两侧都有余额时，锁会记在相反义务上，但结算 `consumeOrderLock` 按锁定代币取对应侧量、划转仍以签名 Fill 金额为准且受余额校验兜底，无法超签名量动账——最坏是该单的担保口径错位 + maker 需一笔 release 纠正。缓解（设计稿 §4.2 既定纪律，本轮再次确认）：落锁后必须读回 `orderLocks` 的 (token, remaining) 与本意比对，不一致立即自助释放并告警；生产路径的节点 `LockOrder` 由订单 side 派生标志（`ObligationForOrder`），不靠猜 |
| 5 | **共享余额先到先锁的排序挤占**：同一 maker 多张已签订单共享同一份 Vault 余额（签名免费，义务总和可超余额），第三方先锁 A 单会占用共享余额，使 maker 本意优先的 B 单暂时无法落锁 | **真实存在，但不构成实际 DoS** | ①被锁的 A 本就是 maker 亲自签名同意的条款，A 成交是合法结果而非攻击收益；②排序可由 maker 以**一笔 release + 一笔重落锁**自助重排（无时间锁、无需任何人同意），攻击者每重复骚扰一次都要再付一笔 lock gas 且必须持有 maker 的有效签名订单——maker 停止超签后攻击面即消失；③占用有 `expiresAt` 硬上限，过期锁任何人可释放；④偿付安全不受影响：合约恒维护 `locked ≤ balance`，超签只影响自家订单的先后，不影响任何第三方资金。定性：这是「maker 自家已签意图之间的排序问题」，不是可用性攻击 |
| 6 | 无权限落锁给中继/前端带来垃圾锁灌水 | **不成立为新增面** | 落锁 gas 由落锁者自付，协议资金零消耗；且一笔已落锁订单必然有真实签名 + 真实余额背书，按设计稿 §1.2 的链上过滤口径，它是比未落锁订单**更可信**的簿上条目 |
| 7 | 重复落锁 / 落锁-结算竞态 | **不成立** | 判重按 digest 与调用者无关（forge 覆盖换人重复锁 revert）；结算消费仍仅 Settlement 且与划转同事务，L2 未改 `consumeOrderLock` / `release*` 任何权限与语义 |

**低成本缓解的落地情况**：①链下预检（提示性）：节点 `LockOrder` 本就先查
既有锁与可用余额再发交易（第 27 轮幂等逻辑），L2 后该预检对任何落锁者同样
适用——它只省 gas、**不改变链上语义**，本文不把它表述为安全机制；②操作
建议（写入 §7 使用说明）：maker 不要签义务总和超过 Vault 余额的订单组
（若在意优先级）；任何人落锁后应读回 `orderLocks` 校验方向与金额；
maker 发现被抢锁/错锁时一笔 `releaseOrderLock` 即可纠正。③**不做**合约层
优先级队列/落锁 bond：需改订单签名格式（三方协同）或引入质押经济，与
「一笔交易即可自助纠正、上限由 expiresAt 兜底」的实际风险量级不成比例；
主网前若真实出现排序争议再评估。

## 7. 如何使用 L2 落锁（使用说明）

**干什么**：任何人（maker 本人、taker、公告栏/中继运营方、机器人）都可以
替一笔已签名订单把其付款义务在 Vault 里锁住，订单才可被结算。挂单不再
依赖运营节点在线落锁。

**使用前提**：订单必须是有效的 EIP-712 签名订单（按当前 Settlement 域
签名）、未过期，且签名者在 Vault 里有足额可用余额。

**操作步骤**：调用 `Vault.lockForOrder(order, signature, payWithTokenIn)`
——卖方（付 tokenIn）传 `true`，买方（付 tokenOut）传 `false`；金额不用传，
合约从订单派生。落锁后读回 `orderLocks[digest]`，核对 (user, token,
remaining) 与本意一致。

**注意事项**：①同一订单只能落锁一次，重复调用 revert；②方向标志写反
多数情况下会因另一侧余额不足 revert，若两侧都有余额则须靠读回校验发现
并用 `releaseOrderLock` 纠正；③改主意时 maker 本人一笔 `releaseOrderLock`
即可解锁，过期后任何人可释放；④maker 不要签义务总和超过 Vault 余额的
订单组（在意成交优先级时）。
